再谈vibe coding

2026-05-16 18:58
体验vibe coding已经一月，蜜月已过，渐渐地对vibe coding祛魅。回归平静之后，发现在上下文较短的简单任务场景中，如就某一个知识点展开理论上的辨析，或利用AI就某一个课题写一课时的教案，在这方面AI的表现堪称出色和完美。有时在讨论的过程中，甚至能帮你纠正和打磨之前错误和偏差的认知，与人碰撞出思维的火花；当然，在vibe coding过程中，也存在一些很难发现的“隐性问题”和埋藏在提示词和上下文中的“边界地雷”，稍有不慎就会踩中，其带来的后果就是差之毫厘，失之千里，最终会导致刚刚建好的摩天大厦轰然倒塌，也就是程序压根不能用。下面就这两种使用场景记录一下自己vibe coding真实体验。

我用自己打造的AI伴读agent让自己读懂了鲁迅。通过编写工作流文档，我打造了一个集学术写作、文学沙龙讨论以及基于苏格拉底诘问法教学风格的文本研读“导师”。我们通常会从一个具体的问题，如“如何理解鲁迅《希望》中‘绝望之于虚妄，正与希望同。’这句话”谈起，一直谈到鲁迅当时的心理状态和写作时代背景，包括鲁迅先生作品被选入课本时选择性删节问题的看法。将近10轮的对话内容， 我的AI伴读自动帮我整理成将近9000字的文稿。按照我定义的流程和步骤，自动归档上传到我的知识库，成为我个人私有的读书笔记。我想这是任何一场学术沙龙，任何一场师生对话都无法做到的，因为要将口头的对话用文字一字不漏地记录下来，本身就是极难极繁琐的一件事，更何况是在由提问者主导的即兴讨论的场景下呢？在这样的场景中，对于即兴问题的回答让我充满期待，由问题的回答可以让我在答案中产生对新问题的好奇，真正地让我打破砂锅问到底。每当看到黑色的命令行窗口中出现“Thinking…”的字样 ，我的思绪便会被那不断闪烁的省略号所牵引，仿佛那三个点的背后藏着通往新世界的大门。看着屏幕上一行一行刷出来的黑底白字，曾经觉得枯燥无比的终端命令在AI的加持下，又一次展现出它的无穷魅力。只不过它这次带来的不再是主宰一切的笃定与果决，而是传递着对知识满心的欢愉和热忱。这种氛围感的渲染我觉得恰恰切中vibe这一单词的要义，也许从coding的角度来说，这一场景并不能算是严格的编码过程，但从广义的角度来说，我和AI探讨，归档和记录的过程何尝又不是对知识的再编码呢？更何况在对于编码问题的探讨中，AI对于抽象理论的神妙比喻，也让我叹为观止：在对于“数组指针”和“指针数组”这一对抽象编程概念的解释过程中， AI用酒店房间这一场景生动的比喻了两者之间的关系和不同，用简短的口诀让原本极其枯燥难辨的理论概念变得生动起来。现将这段比喻摘录在此：指针数组 = 数组，里面装指针。类比：酒店一层5间房，每间只放一把房门钥匙，钥匙开不同客房；数组指针 = 指针，指向一个数组，类比：酒店对应楼层的门禁卡，权限直接对应这一层连续的5个客房。AI依靠它庞大的知识库和强悍的联想能力，真正满足了我情境化学习和深度探索两方面的需要。这种通过比喻营造出来的氛围感，其实对于学习者来说是非常有帮助的。只要定义好清晰的工作流水线，就可以打造个性化的专任辅导教师，在某种意义上由AI实现真正的因材施教。当然，这一切有个前提就是学习者本身要有疑问，要有探索知识的欲望，本身对学习者要求较高，要求其有独立思考的能力。

另一方面，在工程实践中，vibe coding其实也给我带来了不小的困扰。前一段时间谷歌员工写了一篇标题为《The 70% problem: Hard truths about AI‑assisted coding》的论文，标题翻译过来是“70%难题：AI编程的残酷真相”。这篇论文其中核心观点可以概括为一句话：
AI帮你快速写出70%代码，但剩下30%的审查、排坑、兜底工作，反而让程序员工作强度暴增、压力更大。
也就是说，AI写代码速度变快，但代码审查变成了最大瓶颈；初级工程师疯狂出代码，资深工程师被审查、纠错、排查逻辑漏洞压垮，工作量不降反升。
而不幸的是，我感觉我自己正陷入了这样一种困境中。从传统意义上来说，算法的核心就在于自身的确定性，每一个输入必定会得来确定的输出。而AI背后的算法却大不相同，原理是依靠概率和大数定理。用一句通俗的话来说，传统算法靠人定义因果；AI靠概率抓统计共性。所以从理论上来说，只要指令锁死范围，概率最优解≈人类视角下的准确解，而且不用人穷举所有规则，所以效率暴涨。但现实的问题就在于：作为单个个体来讲，个体具备的经验不同，对系统设计的理解不同，个人无法做到全知全能。我们并不确定自己给出了指令是否正确，AI输出的答案是否真的能奏效。因为AI拥有我们无法企及的知识库。就拿我自身来说，在写提示词的时候，我的感觉是，除非我在写提示词之前就已经对整个项目以及整个系统的每个设计运行步骤都有非常清晰的认知，只有基于这样的前提，才能去给AI下达准确无误的指令，或者说我才能有能力去判断AI输出的答案是否符合我的预期。可问题在于：既然我清晰的知道了系统设计的每一个步骤，那我为什么还要让AI去告诉我怎么设计呢？我们利用AI coding，AI 设计，一方面不就是为了弥补自己思维上的考虑不周吗？打个比方，以前我们都说面试造火箭，工作拧螺丝，现在是你真的要去用AI造火箭的时候，你会发现你必须要站在工程总设计师的角度去剖析火箭的真正结构才有可能用AI去设计出火箭。但问题是你本身可能并没有造火箭的能力，以前没有AI的时候，可能你只是按照总工程师的指示把一个又一个的螺丝拧起来而已，你真的的造出了火箭。通过局部拧螺丝的过程，你慢慢的去理解了火箭是怎么造出来的，这就是经验的积累过程；但现在不同了，全面AI化了，工程师告诉你，我要造一个火箭，你和AI去探讨吧。当视角变成了以需求出发的视角，我发现对于AI应用者的要求提高了。而这一切过程中，应用者还要排除AI幻觉的干扰，清醒的认知到那股不确定氛围下带来的隐藏“边界风险”，建立对“回归错误”的防线，在AI的谄媚中保持清醒独立的判断和认知其实是非常难的。因为人的思维有一种惯性，有一种倾向性，容易被从众心理所影响，这或许是我们思维中的惰性吧：如果没有AI的干扰，我们的思考是独立的，我们清晰的知道思维的路径。但是，当AI为我们提出方案的时候，除非方案本身和我们自己预想的有非常大的偏离，否则这种隐性的错误引导我们很难察觉。而对于错误判定的基本能力又是在不断的经验累积过程中渐渐获得的，如果缺乏对项目的既有经验，就容易被AI牵着鼻子走，这只是其一。

其二，vibe coding 本身的核心理念是对于自然语言的描述进行处理，强调的是一种氛围感，这种说不清道不明的感觉往往就背离了传统算法中定义的确定性，不知不觉中，我们对于AI会产生信任危机，AI也有可能由于不同的上下文，对同样的提示词产生完全相反的理解。还是举一个例子：前几天我和朋友聊天时，他说了这么一句话。“有好消息告诉你”。在当时的上下文中，这句话既可以理解成：我有一个好消息告诉你。还可以理解成：如果有了好消息，我就告诉你。所以站在我的视角，有好消息和没有好消息是两种截然不同的理解，完全会影响我们后续对话的走向。假设把当时的我换成AI,那么如果提问者没有意识到这个问题，AI给出的解决策略，可能就会把提问者引向两个完全相反的方向，这种自然提示词语义上的歧义所产生的不确定现象业内把它叫做“语义漂移”，这就是我开头所提到的失之毫厘谬以千里的致命后果。vibe coding 所带来的语义模糊性就像一颗不定时炸弹，埋在你无法探知的思维死角里。这种模糊的无法掌控的感觉也是让很多程序员唏嘘不已的原因，我在互联网上看到一个说法：当AI自动生成的代码超过1万行的时候，那么整个程序对于人来说可能就是一个盲盒，AI在那儿不停的输出代码，最后结果怎么样在打开盒子那一刻之前你是不知道的。个人非常认同这个看法。对于大型工程来说，我们的代码通常在几十万行左右，而且不同的模块对应不同的微服务，每个微服务就可以把它看作是一个子系统，如何让这些子系统有条不紊地协作，需要我们对每一个零件、每一行代码精打细磨才能得到精确无比的计算结果。而把这样精确的结果输出寄托在AI自动编码和边界审计上，显然是极其不稳定的。如何把AI从偏离的路径上拉回来这也是一个非常值得思考的问题。从软件工程的角度来说固然可以经由对于系统的测试和试运行来解决这一问题，但是所付出的人力和修正成本往往是大于手动编码的，这也正是我目前所面临的困境。

针对以上的问题，我也思考了很久，最终只能得出一个大致的原则：尽量去明确划定每一句提示词的边界，用清晰的语言去描述自己的需求；另一方面相信程序测试运行的精确结果，对AI输出的一切存疑。但这一切需要有一个前提，也就是我得意识到问题的存在，如果我自身的经验不足以让我意识到问题的存在，就会顺应AI做出主观上想当然的判定，进而造成更大的问题。所以个人最终的结论是，在vibe coding时代，我们应该更加注重团队协作、团队讨论，尤其是同行审计的重要性。让团队的智慧来弥补自己思维认知上的不足与局限。这个过程对于AI学习者，以及想要通过AI提升团队工作效率的群体来说无疑是一个艰难的过程，而我们自身对于工作积累的经验，自身所具备的系统性思维，也正是在ai编程时代下我们存在的意义。尽管AI能够“蒸馏”我们的知识，但对于系统性思维和全局最优解的探索，仍然是我们人类胜过AI,强过AI的地方，因为AI对自然语言处理的底层逻辑仍然是寻找局部最优解，在当前条件下，找出最符合语境意图的回答。这是目前AI算力决的上限定的，我不确定将来AI会不会取代人类工作，但我可以肯定的是在创造性，系统性思维这一方面，我们人类仍然有着自己独树一帜的优势，这也正是我们千百万年来进化的最终成果，也是我们成为万物之灵的关键。

vibe coding，用氛围编码打造更好的世界这样的观念和想法无疑会成为今后科技生产的主流方式，但是在创造更好的氛围之前，我们先想一想能否让机器真正读懂我们藏在语言背后的那一股无法传递，捉摸不透的氛围吧。
